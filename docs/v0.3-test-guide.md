## 0. 前置准备

- 必须用 PostgreSQL 后端(file 模式 `/goal` 不会启用、Memory 健康巡检也不会跑)。Onboarding step 2 选 PostgreSQL,DSN 填好。
- pgvector extension 必须装好。启动日志看到 `pg: pgvector readiness probe ok` 才算正常。看到 `pg: vector readiness probe failed` 就先 `CREATE EXTENSION vector;`。
- agent workspace 目录(默认 `~/.pawnix/agents/<id>/`)需要可写——todo.md 写在这里。

启动:
```bash
go build -o pawnix ./cmd/pawnix
./pawnix
```

打开 `http://localhost:18953/chat/`,选一个 agent。

## 1. 可打断 — Mid-run Steering

**怎么试:**

1. 给 agent 发一个会跑多轮 tool 的长任务,例如:
   ```
   分析 trading_journal 表里近 30 天我的交易模式,先按 ticker 聚合胜率,再算每只股票的平均持仓天数,最后给出风险偏好评估
   ```
2. 等 agent 开始跑 tool(看到 `tool_call` 气泡)。
3. **不要等它完**,直接在输入框打字:`重点看 002812`,回车。
4. 应该看到:
   - 输入框下方提示语变成 `Responding…  ↵ Steer (queued for next step)`
   - 右侧出现 `Steer` 按钮(蓝色描边)
   - 点 Steer / 直接回车后,聊天流里出现一个**虚线右对齐**的小气泡,头部 `↳ steer` `queued`(琥珀色 badge)
   - agent 跑完当前 tool 之后,下一个 LLM 调用之前,steer 气泡 badge 翻成 `applied`(绿色),agent 在新的回复里明显 pivot 到新指令上

**容易踩坑:**

- ❌ **steer 不会打断当前 tool**——不要期待它能立刻终止 `web_fetch`。它只在 ReAct 循环的两轮之间生效。要硬停按 **Stop**(红色按钮)。
- ❌ **task 已 done 时发 steer 会失败**——气泡内容会附加 `(task finished — send as new message)`。直接重新发即可。
- ❌ **steer 不能带附件**——附件只属于第一次 `/submit`。模型已经在跑就别想中途加图,先停掉再发新一轮。
- ❌ **Telegram / Discord channel 不支持 steer**——这一版只在 Web UI 接通了 `/api/chat/tasks/{id}/steer`。

**调试看 SSE:**
浏览器 DevTools Network → `events` 流,应该看到 `steer_queued`(后端 ack)和 `steer_received`(agent 真的读到了)。两个事件之间隔的时间 ≈ 当前 tool 跑完所需时长。

## 2. 可围观 — `/plan` Slash + Todo 进度面板

**怎么试:**

1. 输入:
   ```
   /plan 复盘今天恩捷股份的走势并给出明日操作建议
   ```
2. 应该看到:
   - 蓝色虚线气泡,头部 `plan` + `drafting…` badge(琥珀色)
   - plan 文字一行行 stream 出来,3-7 步,**Step 0 或 Step 1 必含 `write_file('todo.md', ...)`**
   - 末尾出现 `▶ 继续执行` / `✎ 调整方案` 按钮(蓝色描边)
3. 点 **▶ 继续执行**:自动发 `go`,agent 进入正常 ReAct 模式,**第一件事写 todo.md**。
4. todo.md 一旦写出,messages 区**最上方**出现一个 `todo.md 0 / N` 横条:
   - 每 3 秒轮询一次,文件变了 UI 自动跟
   - 每个 checkbox 行渲染成对勾框 + 文本,完成的画绿勾 + 删除线
   - 点头部可以塌缩
5. 不满意 plan?点 **✎ 调整方案** → plan 整段进输入框,你改 → 直接发(不要再加 `/plan`,改完的就是新 plan 反馈)。

**容易踩坑:**

- ⚠️ **模型可能不写 todo.md** —— planModeNudge 已经强力要求,但弱模型(deepseek 之类)有概率忘。如果发现 plan 步骤里没提 todo.md,自己加一句 `把这些步骤写成 todo.md` 再发。
- ⚠️ **todo 面板只识别标准 markdown checkbox** —— `- [ ]` / `- [x]`(`* [X]` 也行)。`☐ 任务` 这种 unicode 不识别;模型偶尔会自创格式,看到面板没出来检查 todo.md 的实际格式。
- ⚠️ **完整跑完前面板不会消失** —— 即使所有项打勾,文件还在,面板还在。手动 `rm ~/.pawnix/agents/<id>/todo.md` 清理。
- ⚠️ **`/plan` 期间 tools 是禁用的** —— 模型这一轮不能调任何工具,只能写文本 plan。下一轮(`go` 之后)才能用工具。如果 plan 里看到模型说"我已经查了 X",那就是它在编——这正常,纠正它就好。

## 3. 可托管 — `/goal` 长目标

**怎么试:**

1. 输入:
   ```
   /goal 盯着恩捷股份突破 85 提醒我,跌破成本线 5% 强提醒
   ```
2. 立即看到 agent 回复:`✅ Goal set: ...`,然后**自动**发起一轮 continuation——这是 `TryFireContinuation` 在创建后立刻 fire 的第一条 prompt。模型会读到 `<goal_context>`,开始用 `web_search` / `db_query` 查实时价。
3. 之后**你每次发任何消息**(不是 `/goal` 子命令),turn 结束后会自动触发新一轮 goal continuation——agent 会在每次回复后再继续 audit goal。
4. 看状态:
   ```
   /goal
   ```
   返回 `**active**: 盯着恩捷股份... _tokens used: 8421_`。
5. 暂停:
   ```
   /goal pause
   ```
   `▶ Goal paused.`,后续 turn 不再触发 continuation。
6. 恢复:
   ```
   /goal resume
   ```
   `▶ Goal resumed.`,立刻 fire 一条 continuation。
7. 清除:
   ```
   /goal clear
   ```
   `🗑️ Goal cleared.`。

**容易踩坑(重要)**:

- 🚨 **每个用户消息都会 fire 一次 continuation** —— 这是 v0.3 的简化策略:不用 PostTurn hook 系统,直接在 `runPostTurn` 后调一次 `maybeFireGoalContinuation`。意味着只要 goal 还 Active,你每说一句话 agent 都会**多跑一轮**。
  - 好处:不会"忘记"目标
  - 坏处:**烧 token**。你随便闲聊一句"今天天气不错"也会触发一次 goal 长 audit
  - 应对:**用完 `/goal pause` 或 `/goal clear`**,不要长期挂着。这一版的 goal 设计明确是给"我现在要专注盯一件事"用的,不是"24/7 监控"。
- 🚨 **Goal 没有默认 token budget(unbounded)** —— 没设上限,你 `/goal pause` 之前会一直续命。建议跑前心里有数,跑完看 `/goal` 显示的 `tokens used`。后续版本可能会加 `/goal budget <N>` 子命令,这版没有。
- 🚨 **每 (channel, chatID) 一个 goal**—— `session_key = channel:chatID`。同 agent 多个 chat 互不影响;但同 chat 内 `/goal` 第二次会报 `already exists`,要 `/goal clear` 才能换目标。
- 🚨 **Goal continuation 不会嵌套** —— 已经做了防 tight-loop 的 short-circuit:如果当前 turn 自己就是 goal-fired (`Origin == OriginGoalContext`),不会再 fire 新一轮。所以 goal 连续 audit 是"用户输入 → goal 续命 → 等下一个用户输入",不是无限自走。
- ⚠️ **Goal continuation 的 prompt 模板很严格** —— 模板要求模型做完整 audit(列举 requirements、找 evidence、判断 done/partial),不让它草率宣布完成。**模型可能会觉得自己 done 了但模板压住它继续工作**——这是设计意图,不是 bug。要主动结束就 `/goal clear`。
- ⚠️ **重启 daemon 不会丢 goal** —— 写在 PG 的 `agent_goals` 表,持久化。但 in-memory bus 会丢——重启后第一次发消息才会重新触发 continuation。

**调试 SQL**:
```sql
SELECT id, agent_id, session_key, status, tokens_used, objective
FROM agent_goals
ORDER BY updated_at DESC;
```

## 4. delegate_task(v0.4 储备特性,可选验证)

**怎么试:**

让模型自己用就行——不需要 slash。当用户发"分别给我看 trend-trader 和 dragon-hunter 两个账户的最近 5 笔交易",模型如果觉得任务可分,会自己调 `delegate_task`。

**强行触发的 prompt:**
```
我有两个交易账户(trend-trader 用中山证券,dragon-hunter 用平安证券)。
请用 delegate_task 工具分别派发两个独立子任务,每个子任务从 trading_journal 拉对应账户最近 30 天的交易,
按 ticker 聚合统计胜率/平均持仓天数。最后把两份结果合并成一张对比表。
```

**容易踩坑:**

- ⚠️ **Sub-task 是 SERIAL 不是 PARALLEL** —— 即使模型一轮发 5 个 `delegate_task`,后端 `sync.Mutex` 会让它们串行执行。这是为了避免共享 workspace + sandbox 时的写入冲突。结果:N 个并发任务的 wall-time 是 N 倍,不是 1 倍。模型自己应该意识到这一点(tool description 里写了),但弱模型可能不读。
- ⚠️ **Sub-task 看不到 parent 对话** —— 一切 context 必须在 `task` 参数里全部包进去。模型常犯的错:写一个 task 是"继续我们刚才聊的那个分析",sub-task 完全懵。
- ⚠️ **Sub-task 无法嵌套 delegate_task** —— `runDelegatedLoop` 里把 `delegate_task` 从子任务的 toolset 过滤掉了。防爆炸性递归。
- ⚠️ **Sub-task 不写 session,不发 chat 事件** —— 主聊天界面只看到 `delegate_task` 的 tool_call card 和最终的 tool_result,看不到 sub-task 的中间步骤。后端日志可以看到 `subagent_progress` event,前端目前没渲染(下版可加)。
- ⚠️ **Sub-task 默认 15 分钟 wall-time 上限** —— 超时会返回 `ran out of its 15m wall-time budget`,parent 收到 tool error 后应该自己重试。
- ⚠️ **Sub-task 默认 20 iterations**,可以通过 `max_iterations` 参数覆盖。

## 7. 回滚口子

每个特性都有独立的"开关":

| 特性 | 关闭方法 |
|------|----------|
| Steering | 不用就行,Web UI 输入框正常发就走 /submit |
| `/plan` slash | 不用 `/plan` 就不会进 plan 模式 |
| `/goal` slash | 切回 file storage(`storageType: file`)就完全禁用 |
| Todo 面板 | 删除 `~/.pawnix/agents/<id>/todo.md` |
| Memory health 巡检 | 不用关——它只是 log warn,不影响任何路径 |
| pgvector readiness probe | 失败也只 warn,不会 disable memory backend |
| delegate_task 工具 | tool registry 里硬编码,需要代码层面去掉 `tools.RegisterDelegateTask(ag.registry, ag)` 那行 |

**唯一会真破坏既有体验的改动**:agent 现在 system prompt 中 skills section 限制在 ~2k token。如果你之前依赖某个 skill 的全文出现在 system prompt 里,改成走 `load_skill` 工具按需加载即可——所有 skill 都还在,只是 LLM 第一眼只看到 summary。

如果发现行为变化:
```bash
# 启动时看启动日志:
# "skills always-load body exceeds section budget" 表示某些 always-load skill 加起来超了 budget
# 调整办法:在 pawnix.json 里把不必要的 alwaysLoad 项移除
```
